Exposure Bias in Large Recommenders

Dataset: Amazon Reviews 2023 Model: implicit ALS + post-hoc re-ranker Split: temporal leave-last-out Presentation: 02-11-2026 Repo: Vishanth21/exposure-bias-recommenders

We train a standard matrix-factorisation recommender on Amazon Reviews 2023 and show it over-exposes a small set of popular titles; we then add a post-hoc re-ranker that taxes popular items and reallocates exposure to the long tail, and we report exactly what that costs in user relevance.

Presentation is 02-11-2026. Today is 28-10-2026, so we have 5 days, of which realistically ~3.5 are working days. The plan is sized to that, not to an ideal two-week project.

1Definitions we commit to up front

The grader will ask “how did you define popularity?” and “how did you define a small creator?” These are the pre-registered answers.

Concept Operationalisation Why
Positive interaction rating >= 4 → positive. Below → unobserved, not negative. Positive fraction reported. A 4- or 5-star review is what "the user liked it" means, so the threshold is stated as 4 rather than as a fractional cut-off. The card types rating as float and never states the value set, so the loader logs the observed distribution instead of assuming integers. The positive fraction is reported because a skewed scale can make the threshold nearly vacuous.
Item popularity Interaction mass over the catalogue, not item percentiles: head = items covering the first 50% of catalogue train interactions, mid = next 30%, tail = last 20%. Item counts tie heavily at 1–2 interactions, so “top 1% of items” lands inside a tie block and is arbitrary. Mass buckets are stable and directly express the claim “a few items take half the signal”.
Catalogue Items with >= 3 train interactions. Trained on, never recommended. Sensitivity at 1 and 5. An item with one interaction gets a near-random factor, which would inflate coverage and Gini with noise — flattering our own numbers.
Seller size Primary: store_n_items — catalogue items per store. large = stores covering the first 80% of catalogue items, small the last 20% (a mass rule; most stores hold 1–3 items, so a store percentile lands in a tie block). Secondary: store_n_train. Null store rate reported. A real seller identity, not a proxy. Counting over catalogue items means dead listings don’t inflate a store, and item count gives a natural parity benchmark (exposure share ÷ catalogue share). Interaction count is collinear with popularity, so it is secondary.
Exposure Fraction of all recommendation slots an item/bucket receives. Reported as parity (exposure share ÷ item share) as well as raw share. Directly measures what the recommender shows. Parity makes “2% of items take 5% of slots” readable as a number.
Long-tail coverage Fraction of catalogue items appearing in at least one user’s top-K, plus Gini over exposure counts and mean recommended popularity. Standard coverage, with the denominator being the recommendable catalogue rather than all items.
User relevance NDCG@10 and HitRate@10 on the temporal held-out item. recall@10 is not reported separately. With one test item per user, recall@10 == hitrate@10 identically; reporting both would look like two results. NDCG is position-aware and is what the re-ranker costs.

Split and populations

Split: temporal leave-last-out per user — the last positive (rating >= 4) → test, all earlier positives → train, ties broken deterministically. Nothing is dropped at prepare time; ALS trains on every user and item with at least one positive.

Two views are applied downstream, because exposure and relevance need different things:

Population Rule Why it is separate
Exposure pop users with >= 1 train positive Exposure needs no ground truth, so the catalogue-level claim runs on the broad population.
Relevance pop users with >= 2 train positives NDCG/HitRate need a held-out item and a plausible history. Reporting exposure here too shows whether the restriction shifts the picture.

Candidates: catalogue items minus every item the user has already rated, including low-rated ones — a rated item is observed, not a recommendation opportunity. Test items outside the catalogue are excluded, and the dropped fraction is reported in the funnel.

Why there is no minimum-interaction filter. Filtering users keeps only the heaviest, least representative ones, and filtering items deletes the very tail we are claiming to protect — biasing the catalogue toward our own finding before the model is ever trained. ALS tolerates sparse rows, so training loses nothing by keeping them; the populations and catalogue are defined as downstream views instead. A results/prepare_funnel.json records every stage so a reader can see how much tail actually existed.

Key design decisions

Decision What it is Why
Train broad, evaluate narrow ALS trains on every user and item with ≥1 positive. Exposure measured on users with ≥1 train positive; relevance on users with ≥2. A user with one interaction still informs item factors, so filtering costs model quality for no benefit. Separating the populations lets the catalogue claim be made on the broad base without pretending the relevance metrics are measured there.
Candidate generation first Re-ranker permutes the top-200 ALS candidates. It may not introduce new items — asserted as a hard invariant. Isolates the exposure intervention from the relevance model, so the delta is attributable to the re-ranker alone. 200 rather than 50 because a tight candidate set caps the achievable exposure change and can make a sweep look flat for the wrong reason.
Z-scored penalty final = z(score) − λ · z(log1p(pop)), both standardised within each user’s candidate list. λ ∈ {0, 0.1, 0.25, 0.5, 1, 2}. ALS scores have arbitrary scale, so a fixed λ against raw scores trades an unknown amount of rank. Z-scoring makes λ readable as standard deviations per standard deviation. λ = 0 is an exact no-op, giving a clean before/after curve in one plot.
Two baselines, in the critical path MostPop (sorted count vector) and Random (uniform sample from catalogue), both through the same evaluate function. Cheap, and they make the cost interpretable: “we lost 0.004 NDCG” means nothing, “we lost 12% of ALS’s edge over Random” means something. Gate: the relevance-cost claim is only reported after confirming ALS beats MostPop on NDCG@10 for the relevance population. If it does not, there is no edge to spend and the cost sentence is replaced with that finding.
Seller control built in exposure_share_by_pop[pop_bucket][store_bucket] — store exposure within each popularity bucket. If large sellers are still over-exposed among head items alone, the seller effect is not merely popularity. One groupby on data already present, and it is what makes the second claim defensible.
Save per-user arrays results/per_user_metrics.parquet with per-user NDCG/hit per λ. Costs nothing now; makes a paired bootstrap on the cost delta ~15 lines whenever there is time. Bootstrap stays optional; the γ-debiased sensitivity metric is owned work (step 9 of the flow table) and is not.
Seed and log everything Hyperparameters, library versions, per-user score std, funnel counts → results/run_manifest.json. The score std is needed to state the scale the penalty operated at; the funnel is needed to interpret any exposure number.

Stated in the report regardless of whether we compute the sensitivity metric: the relevance cost is measured on observed interactions, which are themselves popularity-biased — tail items are under-observed, so penalising popular items is penalised by construction. The reported cost is an upper bound, and the report says so rather than presenting a confident-looking number.

Data artefacts — 01_prepare.py

data/processed/ratings.parquet
  userId:str, itemId:str, rating:float32, timestamp:int64,
  split:str('train'|'test'|'seen'), seen:bool
  # itemId = parent_asin; split='seen' holds every non-positive rating and
  # is used only to exclude already-rated items from candidates

data/processed/items.parquet
  itemId:str, title:str, store:str, main_category:str, price:float32,
  n_train_ratings:int32, popularity_rank:int32, pop_bucket:str('head'|'mid'|'tail'),
  store_n_items:int32, store_n_train:int32,
  store_bucket:str('small'|'large'|'unknown'), in_catalogue:bool

Both bucket rules are mass rules, not percentiles — item counts tie heavily at 1–2 and store counts at 1–3, so any percentile cut-off lands inside a tie block. pop_bucket: head = items covering the first 50% of catalogue train interactions, mid the next 30%, tail the last 20%. store_bucket: large = stores covering the first 80% of catalogue items, small the last 20%, unknown for missing store — reported separately, never folded into either. Every exposure table carries item share and interaction share per bucket.

Model and result artefacts

results/model/als_factors.npz
  item_factors, user_factors            # full catalogue, no sampled negatives

# the top-200 are taken from that complete ordering. No negatives are sampled for

results/baseline_metrics.json    # keyed by exposure_pop / relevance_pop
results/rerank_sweep.json        # keyed by population, list ascending in lambda
results/sensitivity.json         # keyed by population, gamma-weighted metrics
results/rerank_scores_lambda_<L>.parquet
results/per_user_metrics.parquet # userId, population, lambda, ndcg, hit

Two populations, sampled. Exposure = users with >= 1 train positive; relevance = users with >= 2. Each is a fixed-seed random sample of n_eval_users = 300000, sorted by userId before the draw so the result is order-independent; the seed is in run_manifest.json. Without the cap, 200 candidates × millions of users makes baseline_scores.parquet unmanageable and multiplies per-user metrics by six lambda values. Both populations carry exposure tables, so we can see whether the >= 2 restriction shifts the picture.

recall is not reported. With one test item per user, recall@10 == hitrate@10 identically; reporting both would look like two results. baseline_metrics.json carries NDCG, HitRate, exposure shares, exposure parity, the store × popularity cross-tab, coverage, Gini and mean recommended popularity, plus MostPop and Random baseline rows.

Metric functions — src/metrics.py

def ndcg_at_k(recs, relevant, k) -> float
def recall_at_k(recs, relevant, k) -> float
def hitrate_at_k(recs, relevant, k) -> float
def exposure_share(recs_all, pop_bucket_of, buckets=('head','mid','tail')) -> dict
def catalog_coverage(recs_all, catalog_size) -> float
def gini(values) -> float

Stdlib only, no numpy or pandas, so the same functions run in unit tests and in the pipeline. Each is unit-tested against a hand-computed toy example with a known expected value — 52 tests today — so A’s code can be trusted before any real data lands.
